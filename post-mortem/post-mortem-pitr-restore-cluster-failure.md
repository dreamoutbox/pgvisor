# Post-Mortem: Cluster Collapse During Incremental PITR Restore

## Incident Summary

| Metric | Value |
|--------|-------|
| **Symptom** | Cluster entered critical failure state with only 1 healthy node (proxy) after executing Point-In-Time-Recovery (PITR) restore with target timestamp `2026-09-13 18:32:49` from Web Dashboard |
| **Duration / Impact** | Total cluster outage: Leader failed to start; Standby nodes 2 & 3 wiped their local data directories and failed replication re-sync |
| **Reproduction** | 1. Insert initial rows -> Full backup `f1`.<br>2. Insert more rows -> Incremental backup `i1-1`.<br>3. Restore `i1-1` with PITR time `2026-09-13 18:32:49`. |
| **Impacted Subsystems** | `pgvisor-sidecar` (`supervisor.rs`, `config.rs`, `main.rs`), `pgvisor-proxy` (`backup.rs`), and logging infrastructure |
| **Root Causes** | (1) Missing `restore_command` in `postgresql.conf` during targeted recovery triggering PostgreSQL fatal exit, (2) silent error swallowing in sidecar `restore_from_snapshot`, (3) premature `pgdata` wiping on standby replicas before verifying primary readiness, (4) unhandled `pg_ctl stop` on empty directories, (5) missing sidecar CLI handlers for WAL `archive` and `restore` |
| **Resolution** | Wired `restore_command`, `recovery_target_time`, and `recovery_target_action` into `postgresql.conf`; added `pgvisor-sidecar archive` / `restore` CLI commands; re-ordered standby re-sync to check primary health *before* wiping data; fast-failed `wait_ready` on child process termination; guarded `pg_ctl` with `PG_VERSION` checks; disabled ANSI escape sequences in tracing |

## Detailed Sequence of Failure

```
[User triggers PITR Restore on Leader Node 1 with recovery_target_time="2026-09-13 18:32:49"]
                                    │
                                    ▼
1. Node 1 Sidecar stops Postgres, extracts snapshot, and creates `recovery.signal`.
   PostgreSQL 18 starts up in targeted archive recovery mode:
   `FATAL: must specify "restore_command" when standby mode is not enabled`
   Postgres crashes and exits immediately (PID 444, exit code 1).
                                    │
                                    ▼
2. Node 1 `supervisor.rs::restore_from_snapshot` loops `wait_ready(30)`.
   Because Postgres process is dead, `wait_ready` times out after 30s.
   BUG: Startup error swallowed by `let _ = self.wait_ready(...)`!
   Node 1 falsely reports HTTP 200 OK: "PostgreSQL restore from snapshot completed".
                                    │
                                    ▼
3. Proxy assumes leader is healthy and initiates `/control/resync` on Standbys (Node 2 & 3).
                                    │
                                    ▼
4. Node 2 & 3 `resync_from_primary`:
   BUG: Immediately wipes local `pgdata` directory BEFORE checking if Node 1 is ready!
   Standbys then attempt `pg_isready -d primary_conninfo` for 15s.
   Node 1 is dead -> `pgvisor-node1:5432 - no response` repeated 15 times!
   Re-sync fails with timeout; Standby `pgdata` is now left wiped and empty!
                                    │
                                    ▼
5. Proxy retries `/control/resync` on Standbys.
   Standby invokes `pg_ctl stop -D /var/lib/postgresql/data/pgdata -m fast`.
   `pg_ctl: directory "/var/lib/postgresql/data/pgdata" is not a database cluster directory` (User Clue).
   All three PostgreSQL nodes are dead. Cluster reports 1 healthy node (proxy).
```

## Root Causes Analysis

### 1. PostgreSQL 12+ Targeted Recovery Requires `restore_command`
In PostgreSQL 12 and newer, `recovery.conf` was removed in favor of two signal files:
- `standby.signal`: Instructs PostgreSQL to boot into standby streaming mode.
- `recovery.signal`: Instructs PostgreSQL to perform targeted archive recovery (PITR).

When `recovery.signal` is present and `standby.signal` is absent, PostgreSQL's recovery engine mandates `restore_command` in `postgresql.conf`:
```c
/* PostgreSQL source: xlog.c */
if (ArchiveRecoveryRequested && !StandbyModeRequested && restoreCommand == NULL)
    ereport(FATAL,
            (errcode(ERRCODE_INVALID_PARAMETER_VALUE),
             errmsg("must specify \"restore_command\" when standby mode is not enabled")));
```
In `crates/pgvisor-sidecar/src/supervisor.rs`, `restore_from_snapshot` previously wrote a fake multi-line `recovery.signal`:
```rust
// Old broken code:
let content = format!(
    "# Generated by pgvisor restore\nrecovery_target_time = '{target_time}'\nrecovery_target_action = 'promote'\n"
);
tokio::fs::write(recovery_signal, content).await?;
```
PostgreSQL 18 completely ignores text inside `recovery.signal` and only parses GUC options (`restore_command`, `recovery_target_time`, `recovery_target_action`) from `postgresql.conf`. Because `restore_command` was missing from `postgresql.conf`, PostgreSQL failed with `FATAL` at boot.

### 2. Silent Error Swallowing in Supervisor Startup Loop
In `crates/pgvisor-sidecar/src/supervisor.rs`, errors during snapshot restoration and standby re-sync were discarded using `let _ =`:
```rust
// Old broken code in restore_from_snapshot:
let _ = self.start(config).await;
if self.child_pid() > 0 {
    let _ = self.wait_ready(config.port, 30).await;
}
info!("PostgreSQL restore from snapshot completed");
Ok(()) // Always returned Ok(())!
```
Even though the `postgres` child process crashed within milliseconds of being spawned, `restore_from_snapshot` sat polling `pg_isready` for 30 seconds, ignored the timeout error, and returned `Ok(())`. The proxy concluded that Node 1 had successfully recovered and proceeded to re-sync all standbys.

Furthermore, `wait_ready` lacked a fast-fail check. If the child process died, `wait_ready` continued looping for the full timeout duration instead of detecting `child.try_wait()`.

### 3. Premature Standby Data Wiping Destroyed Replica State
In `crates/pgvisor-sidecar/src/supervisor.rs`, `resync_from_primary` executed steps in an unsafe order:
1. `self.stop().await`
2. **Clear old data directory** (wiped `self.data_dir`)
3. Wait for primary readiness (`pg_isready -d primary_conninfo`)
4. Run `pg_basebackup` clone

Because step 2 wiped local storage before verifying that the primary was accessible in step 3, any primary outage turned a replica into a corrupt, unbootable node with an empty data directory.

### 4. `pg_ctl stop` on Empty Directories
When the proxy retried `/control/resync` against Node 2 and Node 3, `supervisor.stop()` ran:
```bash
pg_ctl stop -D /var/lib/postgresql/data/pgdata -m fast
```
Because the directory had already been emptied in the previous failed re-sync, `pg_ctl` could not locate `PG_VERSION` and logged:
`pg_ctl: directory "/var/lib/postgresql/data/pgdata" is not a database cluster directory`

### 5. Missing WAL Archive & Restore CLI Subcommands
While `BackupManager` in `pgvisor-core` implemented `archive_wal` and `restore_wal`, `pgvisor-sidecar` was strictly a daemon with no CLI argument dispatch. PostgreSQL's `archive_command` (`pgvisor-sidecar archive %p %f`) and `restore_command` (`pgvisor-sidecar restore %f %p`) had no entry point in `main.rs`.

### 6. ANSI Color Escapes in Container Logs
`tracing_subscriber::fmt()` was initialized with default settings, causing it to emit ANSI escape sequences (`[2m`, `[32m`, `[0m`) into stdout/stderr. When logs were viewed in raw file viewers or exported to `logs/`, these escape codes polluted the output.

## Changes Implemented

### 1. PostgreSQL Recovery Configuration & Signal Lifecycle
- **File**: `crates/pgvisor-sidecar/src/config.rs`
  - Added `restore_command`, `recovery_target_time`, and `recovery_target_action` to `PostgresConfig`.
  - Updated `ConfigGenerator::write_configs` to render these GUC parameters into `postgresql.conf`.
  - Automated `recovery.signal` management: created when `recovery_target_time.is_some()`, cleaned up when recovery is inactive.
  - Added unit test `test_write_pitr_recovery_config`.

### 2. Standby Re-Sync & Startup Hardening
- **File**: `crates/pgvisor-sidecar/src/supervisor.rs`
  - **In `resync_from_primary`**: Re-ordered steps so that `pg_isready -d primary_conninfo` verifies primary availability **before** wiping `self.data_dir`. If the primary is down, standby data remains untouched.
  - **In `restore_from_snapshot`**:
    - Generates `restore_config` with `restore_command = 'pgvisor-sidecar restore %f %p'`, `recovery_target_time`, and `recovery_target_action = 'promote'`.
    - Removed `let _ =`: propagates errors from `self.start(&restore_config).await?` and `self.wait_ready(config.port, 30).await?`.
    - Once Postgres promotes and becomes ready, rewrites `postgresql.conf` to clean up temporary recovery parameters.
  - **In `wait_ready`**: Added `child.try_wait()` fast-fail check. If the Postgres child process terminates during boot, `wait_ready` immediately aborts with the exit status rather than stalling.
  - **In `stop` and `fence`**: Added `self.data_dir.join("PG_VERSION").exists()` checks prior to invoking `pg_ctl`, preventing `not a database cluster directory` errors on empty directories.

### 3. WAL Archive and Restore CLI Subcommands
- **File**: `crates/pgvisor-sidecar/src/main.rs`
  - Added CLI argument handlers before supervisor daemon initialization:
    - `pgvisor-sidecar archive <source_path> <file_name>`: Invokes `BackupManager::archive_wal` to upload the 16MB WAL segment to OpenDAL/MinIO.
    - `pgvisor-sidecar restore <file_name> <target_path>`: Invokes `BackupManager::restore_wal`. Exits with `0` on successful restoration, or `1` when the segment is not found in storage (informing PostgreSQL of the end of the archive log).
  - Configured sidecar startup to set default `archive_command` and `restore_command` on `PostgresConfig`.
  - Added `.with_ansi(false)` to `tracing_subscriber::fmt()`.
  - Added unit test `test_sidecar_cli_args_parsing`.

### 4. Logging & Diagnostic Tooling
- **File**: `crates/pgvisor-proxy/src/main.rs`
  - Added `.with_ansi(false)` to `tracing_subscriber::fmt()`.
- **File**: `dev-dump-logs.sh`
  - Created automated diagnostic script to dump logs from `pgvisor-node 1-3` (and optionally proxy/minio) into `logs/`.
  - Automatically strips ANSI terminal color escape codes (`sed -r 's/\x1B\[[0-9;]*[a-zA-Z]//g'`).

## Lessons Learned & Rules for Distributed Operations

1. **Never Wipe Local Node Data Before Verifying Remote Dependencies**:
   Destructive maintenance actions (such as `rm -rf $PGDATA` for replica re-cloning) must be gated behind a positive health assertion of the remote data source. If the primary is down, the replica must preserve its existing database state.
2. **Never Swallow Child Process Startup Failures**:
   Supervisors must treat process readiness polling as fallible. If a managed child dies during startup, fail fast (`try_wait`) and immediately propagate the failure to callers instead of returning false-positive success.
3. **Respect Engine-Specific Recovery Specifications**:
   PostgreSQL 12+ decoupled recovery signaling (`recovery.signal`) from configuration parameters. Targeted recovery requires `restore_command` in `postgresql.conf`; placing parameters in `recovery.signal` is invalid and causes fatal startup aborts.
4. **Log Streams Must Be Plain Text By Default**:
   Daemon processes running under container orchestrators should disable ANSI escape sequences (`with_ansi(false)`) to prevent log corruption in downstream collectors and analysis tools.
