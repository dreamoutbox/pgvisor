# PLAN: Backup/Restore UX & Dashboard Improvements

Source: `TODO.md` L217-L223. No code in this plan.

## Repo facts (explored)

- Backup metadata: `BasebackupMeta` in `crates/pgvisor-core/src/backup/manager.rs` already has `last_transaction_time` / `last_transaction_xid` (populated in `crates/pgvisor-proxy/src/backup.rs::create_backup`).
- Dashboard backup view: `BackupItemView` in `crates/pgvisor-dashboard/src/models.rs` lacks those fields; table in `crates/pgvisor-dashboard/templates/backups.html`; handlers in `crates/pgvisor-dashboard/src/handlers/backup.rs`.
- Restore: `ProxyBackupService::restore_backup(snapshot_id, target_time)` -> sidecar `POST /control/restore` (`recovery_target_time` in `crates/pgvisor-sidecar/src/control/{state,handlers}.rs`) -> `ConfigGenerator` writes `recovery_target_time` (`crates/pgvisor-sidecar/src/config.rs`).
- CPU/RAM: sidecar `system.rs` + `control/state.rs` already expose `cpu_percent`, `memory_used_bytes`, `memory_total_bytes`; no disk metric yet. Dashboard `nodes.html` / `overview.html`.
- Explorer: `handlers/sql.rs` (`api_list_tables`, `api_table_*`) and `crates/pgvisor-proxy/src/executor.rs` are single-database; no database selection.
- Build/test: `cargo nextest run --test-threads 1 --fail-fast`; integration via `./test.sh` with compose profiles generated by `scripts/generate_test_composes.py`.

## Order rationale

Foundations (metadata surfaced in UI, validation) -> restore features that depend on them (xid, slider) -> independent features (explorer, node metrics, upload).

## Unknowns, risks, assumptions

- Assumption: WAL coverage end can be derived from the newest backup `last_transaction_time` or archived WAL listing; if neither is reliable, upper bound falls back to "now" and Postgres remains the final check (shadow restore already rolls back safely).
- Risk: xid targets only meaningful on the snapshot's timeline; document and validate where possible.
- Risk: Upload size (multi-GB tar) needs streaming and body-limit tuning; Phase 7 is the largest and may need splitting.
- Risk: Restore-related integration tests are slow; run serially per AGENTS.md and use replication-lag polling loops.
- Assumption: Disk metric measured on PGDATA mount via `statvfs`-equivalent from std/available crate (check dependency policy before adding one).
- Open (non-blocking): whether upload accepts only PgVisor-format archives or raw `pg_basebackup` tars; plan assumes PgVisor format.
